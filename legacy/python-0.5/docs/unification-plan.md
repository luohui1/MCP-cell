# MCP 统一运行方案：不是把所有配置塞进一个进程

日期：2026-10-17。状态：架构提案，尚未实现共享运行。基线：0.5.0a1 本地交付，运行层沿用 0.3/0.4 的独占 stdio 转发。

## 决策摘要

MCPcell 是 MCP 运行管理器，不扩张成另一个综合 IDE。MCP 主界面负责服务清单、来源、接入、暂停与还原；检测范围、AI 工具和原有终端是按需进入的辅助功能。界面不掌握实例生命周期，前端操作调用管理 API；执行核心需要能够在没有打开 UI 的情况下工作。

统一分四层：**服务定义统一、客户端绑定独立、协议入口统一、合格实例受控复用**。不能把“列表折叠成一行”或“经过同一个端口”当成进程复用。一个管理器也不意味着一个超级权限域。

## 1. 代码现状与必须修正的方向

| 位置 | 已有实现 | 缺口 |
|---|---|---|
| `discovery.py` | 有界读取，多客户端配置解析，候选指纹 | 进程内 HMAC 是候选比较键，不是长期 Service ID；不代表安全共享 |
| `management.py` | 源配置备份、接入绑定、变更检查与条目还原 | 绑定仍与各客户端的原始服务项关联；没有独立版本化服务目录及授权视图 |
| `bridge.py` | 一个 stdio 启动入口连接管理器；无调用自动重放 | 每原始服务/会话仍有 Python 桥，桥本身也有启动和内存成本 |
| `runtime.py` `Relay.handle` | 收到首个协议帧后创建 `OwnedProcess`；每连接独占 | `initialize` 也会触发启动，不是真正的 tools/call 级按需执行；没有实例池或协议级共享路由 |
| `Runtime.status` | 进程树 RSS 观测，标注非去重总和 | 不是内核硬限额；8 个连接上限也不能限制每个服务的内存增长 |
| `server.py` | 同一状态目录的 InstanceLock、本地认证 API | 必须保持管理/数据通道职责分离，不能由普通工具通道修改任意启动策略 |
| 前端来源过滤 | 0.5 已修正操作范围 | 0.4 中仅显示 Cursor 的分组仍可接入其他同配置客户端；0.5 对分组成员先收窄后操作 |

0.5 未改写上述运行器。只是界面整合、正常浏览器启动及来源操作范围修复，不是 OOM 解决完成版。

## 2. 对象模型：一份定义，多份授权绑定

`ServiceDefinition` 保存稳定 ID、版本、锁定制品摘要、执行类型、本地 argv 或远程端点引用，以及经过核对的能力描述。不保存某一客户端的批准结果。

`ClientBinding` 保存具体客户端、配置文件与条目位置、原别名、作用域、工作区、凭据引用、批准规则、允许的工具集合和迁移备份。只检查/接入某个来源时，操作不得覆盖其他来源。不能按服务名称自动合并不同凭据或项目。

`AccessProfile` 是编译后的授权视图：某个客户端在明确的工作区和授权域中可用的服务与工具。有效授权必须来源于经批准的绑定，不信任桥提交的任意 `cwd` 或客户端自报标签。工作区身份需处理路径别名、大小写、符号链接/重解析点、盘符与 UNC 等平台差异；无法证明等价时分开。

`InstanceKey` 是复用分区：制品摘要 + 已解析启动配置 + 身份/凭据授权域和版本 + 工作区/挂载 + 权限策略版本 + 状态模型 + 协议能力兼容档。它不同于显示分组键。凭据使用受保护引用，禁止将原始密钥写入普通日志或可见摘要。

`Lease` 记录哪个获授权调用方正在使用哪个实例及业务状态。连接、请求、租约和业务状态句柄的生命期分开。策略或凭据撤销后，不能因为已有租约还在就继续给予权限。

示例：同一个文档搜索制品可以只有一个定义，Claude Code 和 Cursor 有两份绑定。如果工作区和授权域相同且该版本已验证可复用，可以指向同一个实例；换成另一个账号或另一个项目时，实例必须重新分区。定义可以共用，权限不能求并集。

## 3. 接入入口：先兼容，再聚合

迁移期保留当前每服务别名的兼容桥，便于小范围试用与还原。但它不是最终轻量形态。

目标是每个客户端/授权配置只连接一个 MCPcell 入口：支持所需 HTTP 语义的客户端直接连接经认证的本地端点；只支持 stdio 的客户端使用尽量小的原生桥，而非每工具一个完整 Python/Node 运行环境。传输能力必须逐客户端验证，不因品牌名称就默认支持。

```
客户端 A ── 授权入口 A ─┐
客户端 B ── 授权入口 B ─┼── MCPcell 路由与调度 ── 可共享实例池
客户端 C ── 授权入口 C ─┘                    ├─ 工作区/会话独占实例
                                            └─ 远程 MCP 连接
```

入口可共享监听服务，但每个请求独立鉴权。独占配置目录内的状态锁保持有效；多个自定义状态目录不能被宣传成“整机绝对唯一实例”。

聚合后工具名可能冲突，使用稳定服务 ID 派生的命名空间与持久别名映射，不依赖服务自报的 `serverInfo.name` 唯一。客户端的旧白名单、autoApprove、deny 和工具全名必须一起迁移。**禁止把多个旧服务的批准规则扩大成一个网关的通配批准。**无法等价转换就阻断并要求重新批准，不以“无感”为名跳过。

旧别名兼容与单入口聚合是两种显式迁移模式；不能同时声称任何客户端都保持完全相同的工具标识又自动折叠成一个新服务。

## 4. 真正按需启动：发现能力不必常驻执行进程

当前“首协议帧启动”会被初始化触发。要改成调用时启动，网关必须成为有能力描述的 MCP 服务，而不仅是字节管道。

建议在经用户批准的导入/刷新阶段，用受限探测获得并验证能力目录快照，或使用可信的已锁定清单。探测本身会执行第三方程序，不能伪装为只读配置扫描。目录至少绑定制品、配置、授权上下文、协议版本和有效期。首次未知服务可能必须短暂启动探测，不能承诺从不启动。

客户端 `tools/list` 可以由有效目录响应；`tools/call`、`resources/read` 等需要后端工作的请求才申请实例。只有协议能力允许且快照有效时才这么做；动态或不可缓存的服务走实连接路径。网关只声明能够正确实现的能力，不重放任意旧握手冒充新后端状态。

当前官方规范将 2026-07-28 与之后称为 modern（每请求元数据），2025-11-25 与之前称为 legacy（初始化握手）。实现必须分别处理，同一套“缓存 initialize”不能覆盖两者。[1]

新版目录缓存需尊重方法、参数、`ttlMs`、`cacheScope` 与变更通知。私有缓存不跨授权域；包含 `inputResponses` 或 `requestState` 的续调结果不缓存。TTL 不是让所有后端周期性启动刷新的任务表。[2]

现代工具集合可以随每请求授权不同而不同，但不能靠某次连接里先调用一个搜索工具，悄悄改变后续列表语义。[3]

## 5. 共享只对可证明兼容的配置开放

第一种：`exclusive`，默认。状态不明、浏览器、数据库事务、绑定进程 cwd、客户端回调归属不明等全部保留独占，但仍可按需启动并回收。

第二种：`scoped_shared`，已审核版本与运行配置下的无会话状态服务，同一授权分区内复用。默认不根据“只读”注解自动批准；注解不是安全证明。[3]

第三种：`resettable_pool` 或显式句柄适配，后续专门做。归还池之前必须重置验证；失败销毁。显式句柄还需要调用者归属检查，不是拿到句柄就有权限。

串行化调用只能减少并发竞态，不能消除上一会话的账号、浏览器、cwd 或内存状态。共享模式的安全前提不能由加锁代替。

实现共享时至少覆盖：

- 请求 ID 映射：下游身份 + 连接代次 + 请求 ID → 上游请求 ID，避免不同客户端同为 id=1 时响应串线。
- 进度、取消、通知、订阅和服务端请求的归属。一个客户端取消不能误杀其他调用，来源不明通知不能默认广播。
- legacy 能力协商和客户端回调的兼容性；modern 每请求元数据及不透明续调状态保持正确路由。
- 实例代次与失效处理：重启后旧状态、游标和待处理调用不能继续绑定新实例假装恢复。写调用断线报告结果未知，不自动重放。
- 租约与在途请求计数：断开一个使用者只释放它的租约；尚有调用或需要保留状态时不能按普通空闲计时回收。

`acquire(key, lease)` 需要单次创建合并，多个并发启动请求等同只排一个创建任务；后端启动并通过能力校验后才发布 ready。清理失败进入隔离，不继续无限重启。

## 6. 资源治理不是多画一个内存数字

既要有全局预算，也要有实例预算和队列/输出字节限额。新实例启动前预留预算，容量不足排入有界队列或拒绝；预热不能无条件创建空闲实例。按客户端公平调度，防止一个会话占满全部槽位。

Linux 使用受委派且实际可用的 cgroup v2 控制器实现进程树级资源限制；不能把无委派权限时的 RSS 轮询杀进程写成同等保障。[4]

Windows 保留并补全 Job Object 的归属、子进程与退出清理，再设置有效的资源上限。Job 内存约束的提交内存语义与工作集/RSS 不同，要分别展示。[5][6]

单个共享进程的内核限制不能变成每请求硬隔离；需要强隔离的工作应使用独立实例。管理器、桥、缓冲和可选终端资源都纳入统计；远程服务内部内存不在本地管理器的保证范围内。

权限限制需要真正的文件系统/网络执行边界与最小权限凭据，不能只检查调用参数。工具返回内容属于数据，不能修改本地策略。已有 Docker MCP Gateway 的容器生命周期、凭据注入与约束可以作为可选执行后端参考，但不要求所有轻量本地用户必须安装容器环境。[7][8]

## 7. 迁移、恢复和可观测性

客户端配置修改必须显示精确作用域。读取原文并保留未知字段，生成补丁，备份字节及权限，写前核对版本，逐文件原子替换与写后校验。跨文件操作用事务记录恢复，不宣称跨文件天然原子性。外部编辑器不配合锁时仍有竞态，报告冲突而不是强制覆盖。

原先已运行的外部 MCP 无法仅靠配置迁移就安全收养。要求客户端断开/重连，确认入口已切换；只管理证明属于 MCPcell 的进程，不按 node/python 名称全局杀进程。

每条服务详情应显示：绑定哪些客户端、独占还是共享、为什么允许/拒绝共享、实例数、有效资源约束、最近失败/清理结果。日常界面保持简洁，详细证据按需打开。不能从日志里没有错误推导“已安全”，也不能从零观测值推导“零资源开销”。

## 8. 实施顺序与完成定义

| 顺序 | 实际工程交付 | 验收 |
|---|---|---|
| A | 稳定服务目录与来源绑定分离，迁移只影响明确来源 | 接入/暂停/还原 Cursor 不改变 CC；同名不同身份不合并 |
| B | 经验证的授权视图与单入口网关，保留兼容路径 | tools/resources/prompts 不越权；别名和批准规则可审计；缓存失效正确 |
| C | 一种服务的合格共享配置 + 租约/消息路由 | 6 个同域逻辑客户端只启动 1 个测试服务；两个账号不共享；取消/崩溃/重连不串线 |
| D | 总预算 + OS 约束 + 启动/回收压力测试 | 大输出有界、闲置可释放、清理失败阻断重启、约束不可用时明确拒绝 |
| E | 按同一执行契约接入更多 CLI 与适配器 | 原生审批不被扩大，动作结果未知不重放；不增加新的管理页签 |

先完成 A–D，不再为了“全能 Agent 中心”扩张功能菜单。实际开发可以先在现有 Python 核心证明协议正确性，再把高频桥和调度核心拆为小型原生进程；不为了语言标签全仓重写。

基准应对比原始客户端启动、当前独占桥、目录按需启动、受控共享四种模式。记录冷/热延迟、所有自有进程的内存、闲置回收、错误率和隔离测试。实例从 S×M 变为按安全域所需数量只是目标模型，不是已测到的节省百分比。
